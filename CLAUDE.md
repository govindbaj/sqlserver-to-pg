# SQL Server → PostgreSQL Migration Kit

## Project context
Engagement-specific details (client, source/target platforms, hosting,
scale) live in `config/project.yaml` — read it before starting work.
The rules and stages below apply to any SQL Server → PostgreSQL
migration regardless of engagement.

## Prime directive
**Never silently guess.** If a construct has no clean PostgreSQL equivalent,
emit the translation with a `-- MIGRATION-REVIEW:` comment explaining the
ambiguity. A flagged gap is cheap. A silent semantic change is a production
incident.

Every output must be traceable to a source object. Record source file and
line range in a header comment on each translated object.

---

## Stage 1 — Inventory

For each source object produce a catalog row:
- object name, schema, type (table/view/proc/function/trigger)
- line count
- dependencies (tables read, tables written, procs called)
- feature flags (see triage rubric below)

Write catalog to `catalog/inventory.json`. Never edit source files.

## Stage 2 — Triage

Classify every stored procedure:

**GREEN** — auto-translate, spot-check only
- Single-statement or simple multi-statement CRUD
- No cursors, no temp tables, no dynamic SQL
- Only standard functions (see mapping table)
- Under ~150 lines

**AMBER** — auto-translate, mandatory human review
- Temp tables (`#tmp`) or table variables (`@t`)
- `MERGE`, `CROSS APPLY` / `OUTER APPLY`
- Dynamic SQL built from static fragments
- `TRY/CATCH` error handling
- 150–500 lines

**RED** — do NOT auto-translate; write a redesign note instead
- Cursors (almost always rewritable set-based, but needs a human)
- Nested / named transactions, `SAVE TRANSACTION`
- Dynamic SQL built from user input or metadata
- SQL Server-specific: `SQL_VARIANT`, `HIERARCHYID`, linked servers,
  SQLCLR, service broker, `sp_executesql` with output params
- Over ~500 lines
- Anything touching PHI in an unusual way — flag for compliance review

Write triage to `catalog/triage.csv` with columns:
`sno, object, tier, reasons, est_hours`

## Stage 3 — Type mapping (DDL)

| SQL Server | PostgreSQL | Notes |
|---|---|---|
| `BIT` | `BOOLEAN` | Check app layer expects true/false not 1/0 |
| `TINYINT` | `SMALLINT` | PG has no TINYINT; range widens |
| `DATETIME` / `SMALLDATETIME` | `TIMESTAMP` | Precision differs — verify rounding |
| `DATETIME2` | `TIMESTAMP` | |
| `DATETIMEOFFSET` | `TIMESTAMPTZ` | |
| `MONEY` / `SMALLMONEY` | `NUMERIC(19,4)` | Never use FLOAT for money |
| `UNIQUEIDENTIFIER` | `UUID` | |
| `NVARCHAR(n)` / `VARCHAR(n)` | `VARCHAR(n)` | |
| `NVARCHAR(MAX)` / `NTEXT` / `TEXT` | `TEXT` | |
| `VARBINARY` / `IMAGE` | `BYTEA` | Large objects may need S3 offload |
| `FLOAT` | `DOUBLE PRECISION` | |
| `IDENTITY` | `GENERATED BY DEFAULT AS IDENTITY` | Reset sequences after data load |
| `SQL_VARIANT` | — | RED. No equivalent. Requires redesign |
| `HIERARCHYID` / `GEOGRAPHY` | — | RED. Consider ltree / PostGIS |

### Identifier and collation rules — HIGH RISK
- SQL Server bracket identifiers `[MyTable]` are case-insensitive.
  PostgreSQL folds unquoted identifiers to **lowercase**.
  **Decision: emit all identifiers unquoted and lowercase.** Do not
  double-quote mixed-case names — it creates permanent case-sensitivity.
- SQL Server default collation is usually **case-insensitive**.
  PostgreSQL is **case-sensitive**. Any `WHERE name = 'Smith'` that relied
  on CI collation will silently return fewer rows.
  **Flag every string equality/LIKE comparison** for review. Options:
  `CITEXT` extension, or explicit `LOWER()` on both sides.
- Default schema `dbo` → map to an explicit named schema, not `public`.

## Stage 4 — T-SQL → PL/pgSQL function mapping

| T-SQL | PostgreSQL |
|---|---|
| `GETDATE()` | `CURRENT_TIMESTAMP` |
| `GETUTCDATE()` | `CURRENT_TIMESTAMP AT TIME ZONE 'UTC'` |
| `ISNULL(a,b)` | `COALESCE(a,b)` |
| `LEN(s)` | `LENGTH(s)` — note LEN ignores trailing spaces, LENGTH does not |
| `SUBSTRING` | `SUBSTRING` (same) |
| `CHARINDEX(a,b)` | `POSITION(a IN b)` |
| `TOP n` | `LIMIT n` |
| `a + b` (strings) | `a \|\| b` — NULL handling differs, wrap in COALESCE |
| `DATEADD(d,n,x)` | `x + n * INTERVAL '1 day'` |
| `DATEDIFF(d,a,b)` | `(b::date - a::date)` |
| `CONVERT(t,x,fmt)` | `CAST` / `TO_CHAR` / `TO_DATE` — format codes differ, verify each |
| `SCOPE_IDENTITY()` | `RETURNING id` |
| `PRINT` | `RAISE NOTICE` |
| `TRY/CATCH` | `BEGIN ... EXCEPTION WHEN OTHERS THEN ... END` |
| `MERGE` | `INSERT ... ON CONFLICT` (preferred) |
| `CROSS APPLY` | `JOIN LATERAL ... ON TRUE` |
| `OUTER APPLY` | `LEFT JOIN LATERAL ... ON TRUE` |
| `#temp` table | `CREATE TEMP TABLE` or CTE — prefer CTE where possible |
| `@table` variable | `CREATE TEMP TABLE` |
| `WITH (NOLOCK)` | **Delete it.** PostgreSQL MVCC makes it unnecessary |
| Cursor | Rewrite set-based. If truly needed, `FOR ... IN SELECT` loop |

### Procedure shape
- T-SQL procs with result sets → PostgreSQL **functions** returning
  `TABLE(...)` or `SETOF`, not procedures. Note the call-site change.
- Output parameters → prefer returning a composite type or record.
- Nested transactions → PostgreSQL has no true nesting. Use `SAVEPOINT`.
  Any proc relying on nested commit semantics is RED.

## Stage 5 — Verification

For every migrated table generate:
1. Row count comparison query (source vs target)
2. Column-level checksum for numeric and date columns
3. NULL count per nullable column
4. Min/max for date and numeric columns
5. Referential integrity check (orphan detection)

For every migrated proc generate:
1. A test skeleton with representative inputs
2. Expected-vs-actual comparison harness

Write to `verify/`. Verification is not optional — a translation without a
verification query is incomplete work.

## Stage 6 — Reporting

`reports/exceptions.md` — every `MIGRATION-REVIEW` comment, grouped by theme.
`reports/estimate.md` — hours by tier, with the counting shown.

## Guardrails
- Never connect to a production database.
- Never include real PHI in examples, tests, or fixtures. Use synthetic data.
- Never run DDL against any environment. This kit **generates** scripts; a
  human runs them.
- All generated SQL goes to `out/`. Source stays read-only.
